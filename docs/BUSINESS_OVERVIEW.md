# Бизнес-описание приложения «Вдвоём» (OurKoshelechek)

> Документ описывает продукт по состоянию дизайн-макетов (`design/*.html`) и текущему коду
> (`../cmd/app/main.go`). Часть функций пока существует только в макетах и не реализована
> на бэкенде — это явно отмечено в тексте.

## 1. Назначение продукта

Приложение для совместного ведения бюджета группой людей (изначально задумывалось как
инструмент для пары — отсюда название «Вдвоём» в макетах). Участники группы видят общий
бюджет, вносят операции (доходы/расходы), делят расходы между собой, ведут бюджет по
категориям и копят на общие и личные цели.

**Целевая аудитория:** пары и небольшие группы/семьи, которые хотят прозрачно и совместно
управлять общими финансами в реальном времени.

## 2. Модель пользователей и групп

> Решение по продукту: модель — **группы/семьи с произвольным числом участников (N ≥ 2)**,
> а не жёстко зафиксированная пара. Дизайн-макеты сейчас реализуют только вариант «Вы +
> Партнёр» (2 участника) — при реализации бэкенда и последующей доработке UI это нужно будет
> обобщить: везде, где в макетах жёстко «Вы / Партнёр», по бизнес-модели должно быть
> «участник группы N».

Ключевые сущности верхнего уровня:
- **Пользователь** — аккаунт с логином/паролем (сейчас — только username/password, см. §4).
- **Группа (бюджет)** — объединяет N пользователей, у которых общий доступ к операциям,
  бюджету и целям группы; изменения видны всем участникам в реальном времени
  (в макетах — фраза «бюджет обновляется у вас обоих в реальном времени»).
- Пользователь может быть участником группы; вопрос множественного членства
  (один пользователь — несколько групп) — открытый, см. §6 «Вопросы».

## 3. Функциональность (по разделам UI)

### 3.1 Обзор (`design/Main.html`, `design/Phone-Main.html`)
- Общий баланс группы и его изменение за месяц.
- Доходы за месяц с разбивкой по участникам (кто сколько внёс).
- Расходы за месяц с разбивкой по категориям.
- Бюджет по категориям: лимит, факт, прогресс-бар, индикация превышения лимита.
- Лента последних операций.
- Навигация по месяцам (переключение отображаемого периода).
- Быстрое добавление операции.

### 3.2 Операции (`design/Transaction.html`, `design/Phone-Transaction.html`)
- Добавление операции:
  - тип: расход / доход;
  - сумма;
  - категория (из справочника: Продукты, Жильё, Транспорт, Развлечения, Здоровье,
    Накопления, Зарплата, Другое);
  - плательщик: конкретный участник или «поровну» между участниками;
  - дата;
  - комментарий (необязательно).
- История операций с фильтром: все / только доходы / только расходы.

### 3.3 Бюджет (`design/Budget.html`, `design/Phone-Budget.html`)
- Распределение общих расходов между участниками в рублях (доля покрытия расходов),
  по умолчанию рассчитывается по соотношению доходов участников за последние 3 месяца,
  с возможностью ручной корректировки (слайдер).
- Категории бюджета: лимит в рублях на месяц на категорию, доля от дохода (%), сумма
  «свободно» (доход минус распределённое по категориям).
- Управление категориями: добавление, удаление, редактирование лимита.

### 3.4 Цели накоплений (`design/Goals.html`, `design/Phone-Goals.html`)
- Сводка: всего отложено, число активных целей, отложено за текущий месяц.
- Цель накопления: название, целевая сумма, текущий прогресс, прогресс в %, прогноз срока
  достижения при текущем темпе.
- Тип цели: **общая** (взносы от нескольких участников, поровну) или **личная**
  (взносы только от одного участника).
- Пополнение цели, создание новой цели.

### 3.5 Настройки
Пункт присутствует в навигации макетов, но содержимого раздела в дизайне нет —
предположительно управление профилем, группой/участниками, категориями и т.п.

## 4. Текущая реализация бэкенда

Реализован **только тестовый сервер аутентификации** (`../cmd/app/main.go`), без связи
с бизнес-функциями из §3. Все операции/бюджет/цели в коде отсутствуют.

Существующие ручки:

| Метод | Путь | Назначение | Заметки |
|---|---|---|---|
| POST | `/register` | Регистрация: `{username, password}` → JWT | Пользователи хранятся **в памяти процесса** (`map[string]string`); данные теряются при рестарте |
| POST | `/login` | Вход: `{username, password}` → `{access_token, token_type, expires_in}` | JWT HS256, TTL 1 час, секрет захардкожен в коде |
| GET | `/me` | Возвращает `{username, role}` из токена | Требует заголовок `Authorization: Bearer <token>` |

Роль (`role`) сейчас вычисляется по имени пользователя (`admin` → `admin`, остальные →
`user`) — это заглушка, не связана с группами/бюджетами.

## 5. Что нужно реализовать (бэкенд под функции §3)

Решение по продукту: **пора добавлять постоянное хранилище (БД)** — переход от
in-memory тестового сервера к реальной персистентности.

Ориентировочный список ручек, которых сейчас нет и которые нужны под функциональность
из макетов (для уточнения и приоритизации — см. вопросы в §6):

- **Группы**: создание группы, приглашение/добавление участника, список участников группы.
- **Операции**: создание/редактирование/удаление операции, список операций с фильтрами
  (период, тип, категория, участник), получение сводки за период (доходы/расходы/баланс).
- **Бюджет**: получение/обновление категорий и лимитов, получение/обновление доли
  распределения расходов между участниками.
- **Категории**: список категорий (дефолтные + пользовательские), создание/удаление.
- **Цели накоплений**: список целей, создание/редактирование/удаление цели, пополнение
  цели (создаёт операцию-взнос).

## 6. Вопросы для уточнения (открытые)

Часть вопросов уже решена в диалоге (модель группы — N участников, нужна БД). Остались
открытые:

1. Один пользователь может состоять в нескольких группах одновременно, или группа
   ровно одна на пользователя?
2. Как участник попадает в группу — по инвайт-ссылке/коду, по email, вручную
   администратором?
3. Нужна ли ролевая модель внутри группы (например, «владелец группы» с правом
   удалять/приглашать/выгонять участников), или все участники равноправны?
4. Валюта — всегда рубли, или нужна поддержка нескольких валют?
5. Какую БД предпочтительно использовать (в `go.sum` уже подтягивается
   `go.mongodb.org/mongo-driver` как транзитивная зависимость — это осознанный выбор в
   пользу MongoDB, или это случайная зависимость и нужна реляционная БД,
   например PostgreSQL)?
6. Нужна ли история изменений/аудит операций (кто и когда отредактировал операцию),
   учитывая, что бюджет общий и правки видны всем участникам?
7. Нужны ли повторяющиеся операции (регулярные платежи — аренда, подписки) как отдельная
   сущность, или это делается вручную каждый месяц?
