# Бизнес-описание приложения «Вдвоём» (OurKoshelechek)

> Документ описывает продукт по состоянию текущей реализации: GraphQL-схема
> (`../api/**/*.graphql`), доменная модель и миграции БД (`../db/migrations/`), и
> фронтенд (`../frontend/src/screens/*.tsx`). Ранее документ описывал статичные
> HTML-макеты (`design/*.html`) — этой директории в репозитории больше нет, фронтенд
> сам стал референсом UI. Часть решений, отмеченных ниже как открытые вопросы, всё ещё
> не реализована — это явно отмечено в тексте.

## 1. Назначение продукта

Приложение для совместного ведения бюджета группой людей (изначально задумывалось как
инструмент для пары — отсюда название «Вдвоём»). Участники группы видят общий бюджет,
вносят операции (доходы/расходы), делят расходы между собой, ведут бюджет по категориям
и копят на общие и личные цели.

**Целевая аудитория:** пары и небольшие группы/семьи, которые хотят прозрачно и совместно
управлять общими финансами в реальном времени.

## 2. Модель пользователей и групп

Модель — **группы с произвольным числом участников (N ≥ 2)**, реализовано как N:M
между пользователями и группами: один пользователь может состоять в нескольких группах
одновременно (`group_members`, `PRIMARY KEY (group_id, user_id)`), и в UI есть
переключатель группы (`GroupScreen`), когда пользователь состоит больше чем в одной.

Ключевые сущности верхнего уровня:
- **Пользователь** — аккаунт с логином/паролем (username/password, см. §4).
- **Группа (бюджет)** — объединяет N пользователей с общим доступом к операциям, бюджету
  и целям группы.
- **Роль участника в группе** (`group_role`): `OWNER` (создатель группы) и `MEMBER`
  (приглашённый участник) — обе роли равноправны почти везде: `@requireGroupRole(min:
  MEMBER)` стоит на всех мутациях группы (переименование, приглашение, удаление
  участника, операции, бюджет, цели), т.е. роль сейчас не ограничивает права внутри
  группы, кроме того, что владелец не может быть удалён/выйти (нет мутации на это).
  В БД и доменном слое (`internal/domain/group`) есть третья роль `reader`
  (только чтение), но в GraphQL-схеме (`enum GroupRole`) она не объявлена и выдать её
  участнику через API сейчас нельзя — см. открытые вопросы §6.

## 3. Функциональность (по разделам UI, `frontend/src/screens/`)

### 3.1 Вход и регистрация (`AuthScreen.tsx`)
Регистрация и вход по username/паролю, выдача JWT (`register`/`login` в
`api/user/user.graphql`).

### 3.2 Обзор (`OverviewScreen.tsx`)
- Общий баланс группы и его изменение за месяц (`GroupSummary.balance`,
  `balanceDeltaMonth`).
- Доходы за месяц с разбивкой по участникам (`summary.income.byMember`).
- Расходы за месяц с разбивкой по категориям (`summary.expense.byCategory`) и по
  участникам (`summary.expense.byMember`, учитывает доли по разделённым операциям).
- Бюджет по категориям: лимит, факт, индикация превышения лимита (из `categories` +
  `summary`).
- Лента последних операций.
- Навигация по месяцам (`period` в формате `YYYY-MM`, используется во всех
  агрегирующих запросах — `summary`, `budget`).

### 3.3 Операции (`TransactionsScreen.tsx`)
- Добавление/редактирование операции:
  - тип: расход / доход (доходы не привязаны к категории — `Transaction.category` = null
    для `INCOME`);
  - сумма (в копейках, `Money`/`MoneyInput`);
  - категория (обязательна для расходов; из справочника группы — дефолтные +
    пользовательские);
  - **плательщик** (`Payer`): либо один конкретный участник (`mode: USER`), либо
    разделение между несколькими участниками (`mode: SPLIT`) — при `SPLIT` можно не
    указывать доли явно, тогда сумма делится поровну между всеми N участниками группы
    (не только 50/50, как в исходном двухучастниковом сценарии), либо задать явные суммы
    по участникам (`PayerShare`), которые должны в сумме давать `Transaction.amount`.
  - дата, комментарий (необязательно).
- История операций с фильтром: все / только доходы / только расходы (`TransactionFilter`
  также поддерживает `categoryId`, `payerUserId`, диапазон дат — фильтры по категории/
  участнику/периоду пока не выведены в UI фильтра, хотя API их принимает).
- Курсорная пагинация (`first`/`after`/`nextCursor`/`hasMore`).

### 3.4 Бюджет (`BudgetScreen.tsx`)
Реализованная модель **отличается от исходного макета**: сейчас бюджет — это план
расходов по категориям (лимит в копейках на месяц на категорию), а не доля покрытия
расходов между участниками. `Budget.income` — справочная величина (сумма фактических
`INCOME`-транзакций за период, равна `summary.income.total`), она ничего не ограничивает
и не используется для расчёта долей. Экран показывает доход по участникам (из `summary`)
как информацию, но **слайдера ручной корректировки доли покрытия расходов между
участниками нет** — разделение расходов между участниками теперь настраивается на уровне
каждой отдельной операции (`Payer`/`PayerShare`, см. §3.3), а не как единая
пропорция на весь бюджет.
- Категории бюджета: лимит в копейках на месяц на категорию (`Category.monthlyLimit`).
- Управление категориями: добавление, удаление, редактирование (иконка, название,
  лимит).
- `totalAllocated` (сумма лимитов) и `free` (доход минус `totalAllocated`, может быть
  отрицательным) считаются на бэкенде.

### 3.5 Цели накоплений (`GoalsScreen.tsx`)
- Сводка: всего отложено, число активных целей, отложено за текущий месяц.
- Цель накопления: название, целевая сумма, текущий прогресс, прогресс в %, остаток до
  цели. **Прогноз срока достижения при текущем темпе (`goalContributions` для расчёта
  «ещё ≈ N месяцев») в UI не реализован**, хотя история взносов доступна через API
  (`goalContributions` query) — см. §6.
- Тип цели: **общая** (`SHARED`, взносы от нескольких участников) или **личная**
  (`PERSONAL`, взносы только от `ownerUserId`; для `PERSONAL` владельцем становится
  создатель цели — сменить владельца или тип после создания нельзя).
- Пополнение цели (`contributeToGoal`) одновременно создаёт операцию-расход в категории
  «Накопления» (категория создаётся автоматически при первом пополнении через
  get-or-create по уникальному имени в группе, см. `idx_categories_group_id_name`) —
  и попадает в общую историю операций и в бюджет по категориям.
- Создание новой цели.

### 3.6 Группа (`GroupScreen.tsx`)
Заменяет собой раздел «Настройки» из исходных макетов (его содержимое там не было
определено). Реализовано:
- Список групп пользователя и переключение активной группы.
- Создание новой группы (создатель = `OWNER`, первый участник).
- Переименование группы.
- Список участников с ролью (владелец/участник), приглашение нового участника **по
  username — участник добавляется в группу сразу**, без подтверждения с его стороны.
- Удаление участника из группы.
- Выход из аккаунта.

Не реализовано: управление профилем пользователя (смена пароля/username), приглашение по
email/коду (см. §6).

## 4. Текущая реализация бэкенда

GraphQL-сервер на Go (gqlgen), схема-first, PostgreSQL как хранилище (goose-миграции,
не MongoDB — см. закрытый вопрос в §6). Архитектура и слои подробно описаны в
[`../CLAUDE.md`](../CLAUDE.md) (`internal/domain`, `internal/service`,
`internal/repository`, `internal/mapper`, `resolvers`). Кратко реализовано:

- Регистрация/вход (`register`/`login` → JWT HS256, `me`).
- Группы: создание, переименование, список, детали с участниками, приглашение по
  username, удаление участника.
- Категории группы: список, создание, изменение (включая лимит), удаление.
- Операции: создание/изменение/удаление, список с фильтром и курсорной пагинацией,
  получение одной операции; поддержка `payer.mode = USER | SPLIT` с равным или явным
  разделением суммы между участниками.
- Сводка (`summary`) за период: баланс, изменение баланса, доходы по участникам, расходы
  по категориям и по участникам.
- Бюджет (`budget`) за период: справочный доход + лимиты по категориям + `totalAllocated`
  + `free` (без доли покрытия между участниками — см. §3.4).
- Цели накоплений: список, создание/изменение/удаление, пополнение (создаёт также
  операцию-расход), история взносов по цели.
- Авторизация на уровне GraphQL-директив: `@requireGroupMembership` (любая роль —
  для чтения) и `@requireGroupRole(min: ...)` (для изменяющих операций, везде `min:
  MEMBER`, т.е. `OWNER` и `MEMBER` равноправны).

## 5. Не реализовано / известные пробелы

- **Роль `READER`** есть в БД и доменном слое (`group.RoleReader`), но не объявлена в
  GraphQL `enum GroupRole` и не может быть назначена через API — приглашённый участник
  всегда получает `MEMBER`.
- **Приглашение по email** — в схеме и таблице `group_invites` заложена возможность
  (`InviteMemberInput.email`, статусы `pending/accepted/revoked/expired`), но
  `internal/service.GroupService.InviteMember` явно возвращает
  `ErrEmailInviteNotSupported` для этого пути; работает только приглашение по username
  (прямое добавление в `group_members`, без подтверждения приглашённым).
- **Прогноз срока достижения цели** («ещё ≈ N месяцев» по текущему темпу) — данные
  доступны (`goalContributions`), расчёт и отображение в `GoalsScreen` не реализованы.
- **Повторяющиеся операции** (регулярные платежи — аренда, подписки) как отдельная
  сущность не реализованы; фактически каждый месяц операция создаётся вручную.
- **История изменений/аудит операций** — таблица `transactions` хранит только
  `created_by`/`created_at`/`updated_at` (последнее изменение), полной истории правок
  (кто и когда что поменял) нет.
- **Управление профилем** (смена пароля/username) — эндпоинтов и экрана нет.
- **Мультивалютность** — не поддерживается: `Money`/`MoneyInput` — это просто целое
  число в минимальных единицах (копейках), без поля `currency`; валюта всегда
  подразумевается одна (рубли).
- Роль `OWNER` не даёт особых прав относительно `MEMBER` ни в одной мутации (`min:
  MEMBER` везде) — нет отдельной мутации на передачу владения или на выход владельца из
  группы.

## 6. Вопросы для уточнения (открытые)

Большинство вопросов из исходной версии документа уже решены в коде (модель группы — N
участников и N:M членство, БД — PostgreSQL, есть роли `OWNER`/`MEMBER`). Актуальные
открытые вопросы, все — про пробелы из §5:

1. Нужно ли выводить роль `READER` в GraphQL API (доменный слой и БД её уже
   поддерживают), и если да — как участник получает эту роль при приглашении?
2. Приоритет реализации email-инвайтов (таблица `group_invites` уже есть, но путь не
   реализован в сервисе) — актуально ли это по сравнению с текущим username-инвайтом?
3. Нужен ли отдельный флоу подтверждения приглашения приглашённой стороной (сейчас
   приглашение по username добавляет участника в группу сразу, без его согласия)?
4. Нужна ли ролевая иерархия с реальными различиями в правах (например, только `OWNER`
   может удалять группу/передавать владение), или текущее равноправие `OWNER`/`MEMBER`
   достаточно?
5. Нужен ли прогноз срока достижения цели в UI, и по какой формуle (текущий темп за
   последние N месяцев, среднее с начала цели и т.п.)?
6. Нужны ли повторяющиеся операции как отдельная сущность, или делать их вручную
   ежемесячно — приемлемо на обозримое будущее?
7. Нужна ли история изменений операций (аудит правок), учитывая, что бюджет общий и
   правки видны всем участникам?
8. Валюта — всегда рубли, или в будущем нужна поддержка нескольких валют (потребует
   добавления `currency` в `Money`/`MoneyInput` и связанные таблицы)?
