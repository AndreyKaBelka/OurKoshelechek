# Правила принятия решений

Читать при изменении схемы БД, API, финансовой модели и перед тем, как объявить задачу
готовой.

## Порядок работы над изменением
1. Найти текущую реализацию функции (фронт → операция `.graphql` → резолвер → сервис →
   репозиторий).
2. Проверить GraphQL-схему в `api/`.
3. Проверить `internal/service`, `internal/domain`, репозитории.
4. Проверить SQL-миграции, FK и уникальные индексы.
5. Только после этого менять код.

## Порядок правок для новой/изменённой фичи
`api/<area>/*.graphql` → `make generate` → `internal/domain/<name>` (struct/конструктор/
репозиторий) → `internal/service/<area>.go` → тонкий резолвер + `internal/mapper` →
при изменении БД `make migrate-create name=…` → `frontend/src/graphql/operations/*.graphql`
→ `npm run codegen` → экран.

## Миграция или код?
- Новая колонка/тип/индекс/constraint → **новая** миграция (выпущенные не трогать).
- Ошибка вида «нет constraint под ON CONFLICT» / FK violation → **не чинить вслепую**
  добавлением UNIQUE/CASCADE. Сначала понять, нужна ли вообще эта запись/связь
  архитектурно (см. `lessons-learned.md`).
- Значение enum в Postgres нельзя удалить — Down-миграция пересоздаёт тип.
- Инварианты «поле обязательно только для type = X» — проверяются в приложении
  (домен/сервис), не CHECK-ом, если так уже сделано рядом.

## Когда спрашивать владельца
- Меняется финансовая модель (что считается доходом/расходом/балансом, как делятся доли).
- Удаляются/переименовываются поля GraphQL, которые использует фронт.
- Решение из списка открытых вопросов в `product-and-users.md`.
- UX-развилка без очевидного дефолта (пример: кнопка «Партнёр» при отсутствии партнёра —
  блокировать или предупреждать).
Во всех остальных случаях — выбрать разумный вариант, сказать о нём и делать.

## Что не должно сломаться при изменении финансовой модели
Существующие транзакции, цели и взносы, бюджет по категориям, доли участников, расчёт
`summary` (баланс, по участникам, по категориям), история операций и её порядок,
существующие GraphQL queries/mutations.

## Чеклист «готово»
- `make fmt vet test` (и `make build`) — без ошибок.
- Изменилась схема → `make generate`, `npm run codegen`, `npm run build`, `npm run lint`.
- Изменилась БД → миграция с Up/Down, `make migrate-up` на локальной базе проходит.
- Для UI-изменений — проверить в реальном приложении, а не только тестами.
- Обновить `context/project-context.md` (статус задач) и, если была грабля,
  `context/lessons-learned.md`.
